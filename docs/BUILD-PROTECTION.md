# XIDER build protection / Защита сборок XIDER

## Owner-requested build / Сборка по запросу владельца

1. In GitHub, open **Actions → Build & Release Standalone Agents → Run workflow** and choose the workflow's current branch so GitHub can load the form.
2. Enter a published `vMAJOR.MINOR.PATCH` tag in the `release_tag` field, then start the run. The workflow checks out and validates that exact tag and records its resolved commit.
3. For a manual run on a version tag, the workflow builds and verifies the packages, then uploads `XIDER-Protected-Build-Inventory`. It does **not** create or publish a GitHub Release. Publishing remains limited to a tag push.
4. Download the separate `XIDER-Components` artifact and its signed `protected-build-manifest.json`. The manifest binds the exact source tag and commit to archive hashes and hashes of every file inside each ZIP. The workflow verifies the Ed25519 signature against the public key pinned by the agents before uploading the report.

The report states `obfuscation.state=not_applied`. XIDER currently compiles Windows and macOS agent binaries with Nuitka, which removes plaintext Python source from those packages; compilation is not obfuscation. The source and server archives are explicitly classified as source bundles. No additional obfuscator is run or claimed. A manual build is a preview: the Windows executable has no Authenticode claim, and the macOS app is unsigned/not notarized. The signed inventory authenticates their exact bytes; it does not replace platform code signing. A signing key is read only from the GitHub `xider-release-signing` environment and is not bundled into client artifacts.

The Windows + macOS source-preview workflow is configured to attach `protected-build-manifest.json` to future tagged releases. That report is signed with the pinned release key and hashes every package member. The Windows Agent and Guard Keeper are reported as compiled; macOS Agent, Guard Keeper, Safari, and Siri are explicitly `not_built` when the release contains only the macOS source preview. A missing native package is never represented as a compiled component.

The protected manifest also records each runtime component separately: Windows Agent, Windows Guard Keeper, macOS Agent, macOS Guard Keeper, and the shared macOS Layers executable used by Safari and Siri. Each row carries its release version, package path, compiler, source-inclusion result, obfuscation state, and entrypoint SHA-256. The manifest builder fails if a required executable is missing or if plaintext source appears in a compiled component archive. Safari and Siri intentionally point to the same executable because they are capabilities in one app bundle, not two independent binaries.

The Telegram version detail reads this component report only after verifying its pinned Ed25519 signature and matching every reported archive size/hash against the separately signed release inventory. The macOS Agent version detail also lists Safari and Siri separately, even though they share one executable. It shows `unknown` when the report is absent or fails verification. This authenticates the publisher's inventory claims; it does not claim that a device has downloaded those exact bytes or that a runtime effect was physically tested.

PyArmor was evaluated and is not wired into release builds. Its current license documentation says the CI license does not work on runners with their own disk, while XIDER's hosted Windows/macOS release jobs use such runners; its Nuitka integration documentation also says that pairing has not been tested by the maintainer. Until a compatible license path and a passing full-package Windows/macOS proof exist, the signed manifest continues to say `not_applied` for every component. See [PyArmor license types](https://pyarmor.readthedocs.io/en/latest/licenses.html) and [PyArmor with Nuitka](https://pyarmor.readthedocs.io/en/stable/how-to/third-party.html).

## Сборка по запросу владельца

1. В GitHub открой **Actions → Build & Release Standalone Agents → Run workflow** и выбери текущую ветку workflow, чтобы загрузить форму.
2. В поле `release_tag` укажи опубликованный тег `vMAJOR.MINOR.PATCH` и запусти workflow. Workflow проверит этот тег, соберёт именно его и запишет разрешённый commit.
3. При ручном запуске на теге workflow соберёт и проверит пакеты, затем загрузит `XIDER-Protected-Build-Inventory`. Он **не создаёт и не публикует GitHub Release**. Публикация доступна только при push тега.
4. Скачай отдельный artifact `XIDER-Components` и подписанный `protected-build-manifest.json`. Манифест привязывает точный тег и commit исходников к хешам архивов и каждого файла внутри ZIP. Перед загрузкой отчёта workflow проверяет подпись Ed25519 по открытому ключу, закреплённому в агентах.

В отчёте указано `obfuscation.state=not_applied`. Сейчас XIDER компилирует агенты Windows и macOS через Nuitka, убирая открытый Python-код из этих пакетов; компиляция не является обфускацией. Архивы исходников и сервера явно отмечаются как содержащие исходный код. Другой обфускатор не запускается и его применение не заявляется. Ручная сборка — preview: для Windows не заявляется Authenticode-подпись, приложение macOS не подписано и не notarized. Подписанный inventory подтверждает точные байты архивов, но не заменяет платформенную подпись кода. Ключ подписи берётся только из GitHub environment `xider-release-signing` и не попадает в клиентские пакеты.

Workflow Windows + macOS source preview настроен на прикрепление `protected-build-manifest.json` к будущим tagged-релизам. Отчёт подписывается закреплённым ключом и содержит хеши файлов в пакетах. Windows Agent и Guard Keeper отмечаются как скомпилированные; macOS Agent, Guard Keeper, Safari и Siri получают состояние `not_built`, если в релизе есть только source preview macOS. Отсутствующий native-пакет никогда не выдаётся за собранный компонент.

Защищённый manifest отдельно описывает Windows Agent, Windows Guard Keeper, macOS Agent, macOS Guard Keeper и общий исполняемый файл macOS Layers для Safari/Siri. В каждой строке есть версия релиза, путь пакета, компилятор, наличие исходников, состояние обфускации и SHA-256 точки запуска. Сборка manifest завершается ошибкой, если обязательный бинарник отсутствует или если в архиве скомпилированного компонента найдены открытые исходники. Safari и Siri ссылаются на один исполняемый файл намеренно: это возможности одной сборки, а не два отдельных бинарника.

Карточка версии в Telegram использует компонентный отчёт только после проверки его закреплённой подписи Ed25519 и совпадения размера/хеша каждого архива с отдельным подписанным release inventory. В карточке версии Agent для macOS Safari и Siri также выводятся отдельно, хотя используют один исполняемый файл. Если отчёта нет или проверка не прошла, бот показывает `unknown`. Подпись подтверждает опубликованные издателем сведения, но не доказывает, что устройство скачало именно эти байты или что функция проверялась на физическом устройстве.

PyArmor проверен, но пока не включён в релизную сборку. В его документации лицензий сказано, что CI-лицензия не работает на runner с собственным диском; XIDER собирает релизы на таких hosted Windows/macOS runner. Документация интеграции с Nuitka также помечает эту связку как непроверенную разработчиком PyArmor. Пока нет совместимого лицензионного способа и успешной проверки полного пакета на обеих платформах, manifest честно показывает `not_applied` у каждого компонента. См. [лицензии PyArmor](https://pyarmor.readthedocs.io/en/latest/licenses.html) и [PyArmor с Nuitka](https://pyarmor.readthedocs.io/en/stable/how-to/third-party.html).
