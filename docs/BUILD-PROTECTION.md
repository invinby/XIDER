# XIDER build protection / Защита сборок XIDER

## Owner-requested build / Сборка по запросу владельца

1. In GitHub, open **Actions → Build & Release Standalone Agents → Run workflow** and choose the workflow's current branch so GitHub can load the form.
2. Enter an existing `vMAJOR.MINOR.PATCH` tag in `release_tag`. The workflow checks out that exact tag and records its resolved commit.
3. A pushed version tag runs the CI gate and builds that exact tag as a prerelease, even when Apple credentials are configured. Tag pushes cannot publish stable releases implicitly.
4. For a manual workflow run, leave both publication switches off to upload only a signed component inventory. Turn on `publish_preview` to publish the selected tag as a prerelease. Stable publication requires the owner to dispatch the workflow against the exact `v*` tag with `publish_stable` on, `publish_preview` off, and `XIDER_MACOS_RELEASE_READY=true`. The protected macOS environment then validates signing and notarization credentials and the packaged apps before the release is marked stable. After publication the workflow dispatches Pages with that same tag.
5. Preview publication does not require Apple credentials. macOS runtime bundles remain unsigned and unnotarized, so this path is not a distributable macOS release.
   Until Apple signing/notarization is configured, the published short macOS installer and quickstart use the exact-tag source-preview bootstrap; unsigned compiled app bundles are attached separately for inspection and owner testing.
6. The private release key is read only inside the protected `svchost-release-signing` environment. The workflow checks that its derived key ID is pinned in `SvcHostMac/release_signature.py`.
7. The component inventory binds the exact source tag and commit to archive hashes and hashes of every file inside each ZIP. The workflow verifies the Ed25519 signature against the public key pinned by the agents before attaching the report to the release or uploading it as `SvcHost-Protected-Build-Inventory`.

Before Nuitka, release builders run the pinned PyObfus 0.11.1 Community tool on the first-party Windows or macOS Python tree. Its offline preflight must report zero parse errors and high-risk findings; syntax and cross-file name checks must pass without executing the obfuscator's output. A privacy-safe `svchost-obfuscation-report.json` records the processed source-file count, transformed-name count, platform, source tree, and verification results. That report is included in each compiled package and its hash is bound into the signed protected-build inventory. The private name map is not generated or shipped. Windows Agent/Guard Keeper are covered by the SvcHostWin tree; macOS Agent/Guard Keeper/Safari/Siri are covered by SvcHostMac. Windows shared helper imports from SvcHostMac and build-only helpers are compiled but excluded from the Windows obfuscation count. Third-party packages are excluded on both platforms.

Obfuscation only raises the effort required to inspect the code; it is not encryption and cannot prevent a determined reverse engineer. Nuitka remains a separate compilation step and is never counted as obfuscation. Source and server archives remain source bundles. GitHub Actions run `41770220559` built Windows and native macOS packages from commit `b56779ad1e332dfac803d8a03047c1278dc37e99`; both platform build jobs and component packaging succeeded. That branch run skipped the release CI gate and publication, so it has no signed component inventory and is not a release. The later prank-hub merge is not in that build; the exact release tag must be rebuilt. The macOS preview has no Apple signature or notarization, and no physical device was tested. The signed inventory authenticates package bytes; it does not replace platform code signing. The release signing key is read only from the GitHub `svchost-release-signing` environment and is not bundled into client artifacts.

The compiled preview workflow attaches `protected-build-manifest.json` to a published preview and hashes every package member. The signed report describes Windows Agent/Guard Keeper and macOS Agent/Guard Keeper/Safari/Siri separately; the latter two share one compiled Layers app. macOS platform-signing status remains `unsigned_preview` until Apple signing and notarization are configured. A missing native package is never represented as a compiled component.

The protected manifest also records each runtime component separately: Windows Agent, Windows Guard Keeper, macOS Agent, macOS Guard Keeper, and the shared macOS Layers executable used by Safari and Siri. Each row carries its release version, package path, compiler, source-inclusion result, obfuscation state, and entrypoint SHA-256. The manifest builder fails if a required executable is missing or if plaintext source appears in a compiled component archive. Safari and Siri intentionally point to the same executable because they are capabilities in one app bundle, not two independent binaries.

The Telegram version detail reads this component report only after verifying its pinned Ed25519 signature and matching every reported archive size/hash against the separately signed release inventory. The macOS Agent version detail also lists Safari and Siri separately, even though they share one executable. It shows `unknown` when the report is absent or fails verification. This authenticates the publisher's inventory claims; it does not claim that a device has downloaded those exact bytes or that a runtime effect was physically tested.

PyArmor was evaluated and rejected for this pipeline because of its hosted-runner licensing and unverified Nuitka pairing. PyObfus is the selected reproducible build-time transformer; the signed status only becomes `obfuscated` when the exact package contains a valid report for its platform/source tree and the component is listed as transformed. A missing or invalid report fails manifest generation. This is build evidence, not a claim that the code is impossible to recover.

## Сборка по запросу владельца

1. В GitHub открой **Actions → Build & Release Standalone Agents → Run workflow** и выбери ветку workflow, чтобы загрузить форму.
2. В `release_tag` укажи существующий тег `vMAJOR.MINOR.PATCH`. Workflow проверит именно его и запишет соответствующий commit.
3. Push version-тега запускает CI и собирает именно этот тег как prerelease, даже если Apple credentials настроены. Сам push тега не может незаметно опубликовать stable-релиз.
4. При ручном запуске оставь оба переключателя публикации выключенными, чтобы только загрузить подписанный component inventory. Включи `publish_preview`, чтобы опубликовать выбранный тег как prerelease. Для stable владелец должен вручную запустить workflow на точном `v*` теге, включить `publish_stable`, оставить `publish_preview` выключенным и иметь `XIDER_MACOS_RELEASE_READY=true`. Защищённое macOS-окружение проверит подпись, нотарификацию и готовые приложения до пометки релиза как stable. После публикации workflow запустит Pages с тем же тегом.
5. Для preview сертификаты Apple не нужны. Runtime macOS остаётся неподписанным и ненотарифицированным, поэтому это не готовый к распространению релиз macOS.
   Пока Apple signing/notarization не настроены, короткий macOS установщик и quickstart используют source-preview bootstrap с точным тегом; неподписанные скомпилированные app-бандлы прикладываются отдельно для просмотра и теста владельцем.
6. Закрытый ключ релизной подписи читается только внутри защищённого GitHub environment `svchost-release-signing`; workflow проверяет, что его key ID закреплён в `SvcHostMac/release_signature.py`.
7. Компонентный inventory связывает точный тег и commit с хешами архивов и каждого файла внутри ZIP. Workflow проверяет Ed25519-подпись ключом, закреплённым в агентах, прежде чем прикрепить отчёт к релизу или загрузить его как `SvcHost-Protected-Build-Inventory`.

Перед Nuitka сборщик запускает закреплённый PyObfus 0.11.1 Community для Python-дерева Windows или macOS. Offline-проверка должна завершиться без ошибок разбора и high-risk находок; проверка синтаксиса и связей между именами должна пройти без исполнения результата обфускатора. В каждый скомпилированный пакет кладётся безопасный `svchost-obfuscation-report.json`: число обработанных файлов, изменённых имён, платформа, дерево исходников и результаты проверок. Хеш отчёта связывается с подписанным protected-build inventory. Приватная карта имён не создаётся и не публикуется. Для Windows Agent/Guard Keeper обрабатывается дерево SvcHostWin; для macOS Agent/Guard Keeper/Safari/Siri — SvcHostMac. Общие helper-модули SvcHostMac, импортируемые Windows-сборкой, и build-only helpers компилируются, но не входят в счётчик обфускации Windows. Сторонние библиотеки исключены на обеих платформах.

Обфускация лишь усложняет чтение кода: это не шифрование и не защита от решительного реверс-инженера. Nuitka остаётся отдельной компиляцией и не засчитывается как обфускация. Архивы исходников и сервера по-прежнему содержат исходный код. GitHub Actions run `41770220559` собрал пакеты Windows и нативной macOS из commit `b56779ad1e332dfac803d8a03047c1278dc37e99`; сборка обеих платформ и упаковка компонентов завершились успешно. В запуске с ветки пропущены CI release gate и публикация, поэтому подписанного компонентного inventory нет и это не релиз. Более позднее слияние пранк-хаба в эту сборку не попало; точный релизный тег нужно собрать заново. Preview macOS не имеет подписи Apple или нотарификации; физические устройства не тестировались. Подписанный inventory подтверждает байты пакетов, но не заменяет платформенную подпись. Ключ релизной подписи читается только из GitHub environment `svchost-release-signing` и не попадает в клиентские пакеты.

Compiled preview workflow прикрепляет `protected-build-manifest.json` к опубликованному preview и хеширует каждый файл в пакетах. Подписанный отчёт отдельно описывает Windows Agent/Guard Keeper и macOS Agent/Guard Keeper/Safari/Siri; последние работают в одном скомпилированном Layers app. Подпись платформы macOS останется `unsigned_preview`, пока не настроены сертификаты и нотарификация Apple. Отсутствующий native-пакет никогда не выдаётся за собранный компонент.

Защищённый manifest отдельно описывает Windows Agent, Windows Guard Keeper, macOS Agent, macOS Guard Keeper и общий исполняемый файл macOS Layers для Safari/Siri. В каждой строке есть версия релиза, путь пакета, компилятор, наличие исходников, состояние обфускации и SHA-256 точки запуска. Сборка manifest завершается ошибкой, если обязательный бинарник отсутствует или если в архиве скомпилированного компонента найдены открытые исходники. Safari и Siri ссылаются на один исполняемый файл намеренно: это возможности одной сборки, а не два отдельных бинарника.

Карточка версии в Telegram использует компонентный отчёт только после проверки его закреплённой подписи Ed25519 и совпадения размера/хеша каждого архива с отдельным подписанным release inventory. В карточке версии Agent для macOS Safari и Siri также выводятся отдельно, хотя используют один исполняемый файл. Если отчёта нет или проверка не прошла, бот показывает `unknown`. Подпись подтверждает опубликованные издателем сведения, но не доказывает, что устройство скачало именно эти байты или что функция проверялась на физическом устройстве.

PyArmor отклонён для этой схемы из-за лицензирования hosted runner и непроверенной связки с Nuitka. Выбран воспроизводимый PyObfus; подписанный статус становится `obfuscated` только когда в конкретном пакете есть корректный отчёт для его платформы/дерева исходников и компонент указан преобразованным. Без отчёта или при неверных данных генерация манифеста падает. Это доказательство сборочного шага, а не обещание, что код нельзя восстановить.
