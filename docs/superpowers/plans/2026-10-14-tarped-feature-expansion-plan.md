# TARPED Feature Expansion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` or `executing-plans` after owner approval. Steps use checkbox (`- [ ]`) syntax; do not begin implementation before approval of this plan.

**Goal:** Turn the approved 510-candidate TARPED catalog into independently testable, owner-verifiable feature releases without changing X-LEX.

**Architecture:** The 17 areas are delivered as six reviewable workstreams, not one oversized patch. A static, versioned Feature Registry describes each feature and binds it to a pre-registered handler; role/grant checks remain enforced by server-side callbacks and agents report explicit result states. Each workstream has its own tests and release gate; physical devices, Telegram, Pages and VPS are separate acceptance layers.

**Tech Stack:** Python 3, aiogram 3, existing MQTT command/result envelopes, pytest, JSON, PowerShell/bash fixtures, GitHub Actions/Pages.

**Spec:** `docs/superpowers/specs/2026-10-14-tarped-capability-expansion-design.md` and the preserved base design `docs/superpowers/specs/2026-10-08-tarped-product-redesign-design.md`.

## Global Constraints

- Source of truth is official `origin/main` commit `6d20370a06eb157428627f9002852514615e8ee2`, recorded in the spec. The latest published release remains v4.2.1; v4.2.2 tag is not a published release.
- Keep X-LEX data, authored text, style selection, runtime behavior and golden tests unchanged.
- Keep the existing three roles `owner/user/guest` plus `blocked`; revalidate access at callback, FSM continuation and execution.
- OS permission is granted only by the owner in the OS UI; never bypass TCC/UAC or fabricate a granted state.
- Location is one-shot and source-labelled; IP estimates never claim GPS or precise coordinates.
- Every arbitrary shell request uses exact, one-time owner approval; new catalog metadata cannot dispatch code by itself.
- Guard Keeper remains visible, locally stoppable and removable; no hidden persistence or anti-owner removal.
- Device/VPS updates require signed artifacts, backup, install, health check and rollback; canary precedes rollout.
- Preserve unrelated tracked/untracked files, including `tools/node_modules/`; never include local `.env`, keys or runtime logs.
- Do not claim physical Windows/macOS, live Telegram, Pages or VPS acceptance without that exact smoke test.
- The catalog currently has 510 unique IDs, 30 per area, and 40 approved replacements; this is a design count, not an implementation count.

## Review Focus

1. A stale or older agent omits a feature ID/result field — bot renders `unknown`/`unsupported`, never success; test in catalog and both agent parsers.
2. Role/grant changes while a form is open — callback/FSM/action gate rejects the stale request; test in bot RBAC and device command handlers.
3. A feature requires an unavailable permission, sensor, OS API or telemetry source — show a source-specific unsupported/unknown state, not a fabricated value; test both platform adapters.
4. A timeout or late reply races with an update/media/shell result — preserve one correlation and truthful terminal state, with no duplicate command; test the owning coordinator.
5. A signed artifact, Pages asset or server bundle differs from its manifest — fail closed or show mismatch/unknown; test release tooling before any publish/deploy.
