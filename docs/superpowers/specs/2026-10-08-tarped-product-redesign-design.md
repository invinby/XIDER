# TARPED — спецификация продуктовой переделки XIDER

Статус: исходная спецификация одобрена для подготовки implementation plan. При проверке плана обнаружено и добавлено уточнение доверия для shell-команд (раздел 10); его следует подтвердить вместе с планом до реализации.

База для аудита: официальный `origin/main` на `984204a8eba1fd42b52c9d344a9e0dbf469eb779`; annotated tag релиза `v4.2.1` имеет tag-object `22acab054c92f4e34641f5556071f6d389a05ed1` и указывает на commit `d7d77a698b763f169327ec99e350ff73f5e34f16`. `origin/main` включает последующие исправления после этого commit.
Область: Telegram-бот, Windows/macOS-агенты, роли и доступы, проверки разрешений, релизы и публичная страница проекта.

## 1. Зачем это делаем

Привести XIDER из набора разрозненных меню и функций к цельному инструменту управления своими Windows/macOS-устройствами через Telegram: предсказуемая навигация, понятные версии, честная диагностика, работающие права и подтверждение опасных команд. Поведение каждой функции должно подтверждаться тестом или явной пометкой «не проверено на устройстве».

**X-LEX не менять.** Не редактировать его словарь, стили, авторские тексты, правила выбора стиля, поведение или тесты. Редизайн может переставить кнопки вокруг X-LEX, но не переименовывает и не переписывает сам X-LEX.

## 3. Что видно в коде сейчас

Факты из текущего исходного снимка `origin/main`, требующие адресной проверки:

1. В `TG-BOT-SERVER/bot.py` есть главный экран, меню устройств и helper `_action_button`, которым пользуются некоторые меню. Статический поиск нашёл 292 вызова `kb.button(...)`; клавиатуры `terminal_menu`, `files_menu`, `screen_menu`, `pranks_menu` и другие строят кнопки напрямую. В файле также 189 декораторов `@router.callback_query(...)`: 132 с `AdminFilter`, 47 с `OwnerFilter`, 8 с `ReadOnlyFilter`, 2 с `AnyAccessFilter`. Это не доказывает обход серверной проверки: часть handlers закрыта фильтрами. Но прямое создание кнопки не применяет UI-фильтр `_action_button`, поэтому возможны несоответствия «кнопка показана, обработчик откажет». Нужен полный callback→menu→handler→permission inventory, а не механическая замена каждого вызова.
2. В `TG-BOT-SERVER/access_store.py` и `roles.py` уже есть роли и проверки доступа по устройству/callback; отложенные формы повторно проверяют права. `menu:server` открыт через `ReadOnlyFilter` для всех незаблокированных ролей, но `server_menu()` показывает управляющие кнопки только владельцу. Сам экран обзора при этом сообщает build ID, состояние MQTT и флаг подтверждения устройств; секреты не выводит. Это надо сохранить как осознанный read-only уровень для гостя/пользователя. Требуется проверить полный путь каждой категории, прямой callback, FSM-продолжение, обновление прав и состояние BLOCKED. Живой Telegram-приёмки нет.
3. Запрос `cmd:capabilities` уже существует. Он сообщает, что объявлено/какие зависимости найдены, а текст бота прямо предупреждает: это не live-тест. Статусы `permission_unverified`, `device_unverified`, `approximate` и другие — честные, но бот пока не даёт для каждой возможности отдельную кнопку повторной проверки/перехода в системные настройки. В `XGENT-MCS/setup_mac.py` есть локальное открытие некоторых панелей macOS Settings; это не Telegram-поток. Соответствующий переход `ms-settings:` в Windows-коде поиском не найден.
4. Геолокация в обоих агентах сейчас получена только по публичному IP (`ipapi.co`/`ipinfo.io`) и уже называется приблизительной, а не GPS. Системного API геолокации и согласованного IP-fallback режима пока нет.
5. macOS-скриншот вызывается через `screencapture -x`; при пустом/ошибочном результате агент возвращает общее сообщение об отказе TCC. Нужно разделять отказ разрешения, отсутствие пользовательской графической сессии, ошибку утилиты и ошибку передачи результата.
6. Владелец может отправить shell-команду выбранному агенту. Перед вводом бот показывает общий экран подтверждения входа в терминал, но после ввода конкретная строка сразу публикуется агенту — отдельной карточки с точным текстом, целью и кнопкой финального подтверждения нет. Оба агента вызывают системную оболочку через `subprocess.run(..., shell=True)`. Нужны одноразовое подтверждение именно неизменяемого текста и аудит до публикации. Текущий HMAC подписывает общий `SHARED_KEY`, который загружают и сервер, и агенты, поэтому сам по себе не доказывает, что команда пришла именно от сервера. Отдельный терминал VPS (`server_ops.run_terminal`) принимает только точные aliases небольшого allowlist диагностических команд и запускает фиксированные аргументы без shell-строки; это не произвольный shell.
7. Поток **«Открыть сайт» уже существует**: бот принимает URL, предлагает количество `1/2/3/5`, проверяет доступ к выбранному устройству, а избранное можно сохранять владельцу. Его надо не писать заново, а проверить и довести до общей модели статуса/дедупликации; существующий диапазон до пяти окон сохранить, пока отдельная проверка не обоснует изменение.
8. `README.md` содержит смешанные русские/английские разделы (21 заголовок верхнего уровня/подразделов в текущем снимке); `README.ru.md` имеет отдельную русскую структуру (10 заголовков), полного взаимного RU/EN-паритета нет. Метаданные GitHub API показывают пустое поле homepage. В отслеживаемом `origin/main` нет `index.html`, `CNAME` или Pages-конфига; из workflows присутствуют только `build-agents.yml` и `ci.yml`, опубликованного workflow для продуктовой Pages-страницы не найдено. `tools/build_pages_entrypoints.py` и загрузка установочных entrypoints в build workflow относятся к установщикам и не заменяют продуктовую landing page.

## 4. Продуктовые правила

- Одно постоянное сообщение-карточка бота — основной интерфейс. Навигация, статусы и ход операции редактируют эту карточку, когда Telegram API это допускает. Не обещать удаление всех сообщений пользователя: Telegram не всегда даёт боту такое право.
- Реальные события безопасности (новый `/start`, подтверждение опасной операции, потеря устройства) отправляются отдельным коротким уведомлением владельцу; они не должны теряться ради правила «одно сообщение».
- Никаких фальшивых процентов выполнения. Показывать этапы («запрос отправлен», «агент отвечает», «проверка здоровья») или реальный прогресс, только если есть измеряемые данные.
- Все опасные операции повторно авторизуются на сервере при фактическом выполнении; спрятанная кнопка не заменяет проверку callback/роли.
- Нет обхода Windows/macOS TCC, UAC или согласия пользователя. Приложение показывает состояние, инструкцию и открывает системную страницу настроек, где это поддерживается; само разрешение выдаёт владелец устройства.
- Сопутствующие процессы `Guard Keeper`, `Safari` и `Siri` должны быть документированными, видимыми как службы/элементы автозапуска и работать только в рамках локально разрешённых возможностей. Не добавлять скрытие, защиту от владельца, анти-удаление или обход системных средств управления. Владелец сохраняет локальный способ остановки и удаления.

## 5. Предлагаемая структура Telegram-интерфейса

### 5.1 Главная карточка

Стабильные верхние разделы:

1. **Устройства** — список с онлайн-состоянием, ОС и версиями.
2. **Сервер** — состояние бота/VPS, нагрузка и доступные серверные операции.
3. **Админ** — только владелец: пользователи, роли, права, события и журнал.
4. **Инфо** — архитектура, версии, словарь терминов и ссылки на документацию.

Видимость и порядок экранов — одинаковые для Windows и macOS; состав действий определяется возможностями устройства и правами пользователя. Возврат «назад» и «домой» ведёт в одно и то же ожидаемое место; переходы не создают новое меню-сообщение.

### 5.2 Карточка устройства

Верх карточки: имя, система, online/offline/unknown, время последнего heartbeat, версия агента, версии доступных companion-компонентов и сводка разрешений. Состояние «offline» выводить только по истёкшему heartbeat с таймстампом и понятным порогом, не по одному пропуску.

Единая сетка категорий, составленная из инвентаря всех callback-кнопок:

- Обзор и диагностика
- Экран и мультимедиа
- Файлы
- Сеть и приложения
- Команды и процессы
- Питание
- Версии и обновление
- Разрешения
- Дополнительные функции/розыгрыши

Каждое действие должно иметь: категорию, callback, требуемое разрешение, допустимые роли/гранты, поддерживаемые ОС, таймаут, тип результата и уровень риска. Не поддержанное текущей ОС действие показывается как недоступное с причиной либо не показывается — единообразно по всему продукту.

### 5.3 Версии и обновление устройства

Отдельный экран конкретного устройства показывает установленные версии агента и компонентов, доступные подписанные GitHub Releases, дату/номер, описание изменений и фиксы. Действия: установить выбранную версию, обновить до рекомендованной, откатить на предыдущую. Перед опасным действием — подтверждение; на устройстве выполняется backup → установка → health-check → автоматический rollback при неуспехе. Не показывать релиз как установленный до подтверждённого ответа агента.

Обновления Telegram-бота/VPS — отдельная серверная карточка, не смешанная с обновлениями агентов.

## 6. Роли и управление пользователями

Модель: **владелец / пользователь / гость / заблокирован**.

- **Владелец** — единственный защищённый `ADMIN_ID`, полный доступ и управление правами; нельзя изменить/заблокировать самого владельца из обычного админ-интерфейса.
- **Пользователь** — доступ только к выданным устройствам и отдельно выданным действиям/кнопкам. Отдельный grant на shell даёт право лишь отправить запрос владельцу; он никогда не даёт права самостоятельно подтверждать или исполнять команду.
- **Гость** — навигация в режиме чтения. Чувствительные данные (локация, изображения/камера, файлы, shell-результаты, подробные серверные логи) по умолчанию скрыты; владелец может выдавать только документированные безопасные права.
- **Заблокирован** — никакие меню управления и callbacks не выполняются.

Админ-экран: список пользователей, роль, последнее действие/посещение, выданные устройства и права, блокировка/разблокировка, журнал и уведомления о новом `/start`. Изменение роли/прав и разблокировка подтверждаются владельцем. Права проверяются одновременно на отрисовке кнопки, при callback, при продолжении FSM-формы и перед публикацией команды агенту; отзыв прав немедленно закрывает текущие незавершённые формы.

Тестовая матрица обязана покрыть каждую роль × навигацию × callback × устройство × отзыв права во время незавершённой операции. Запросы от заблокированного/неизвестного ID должны завершаться отказом без утечки данных.

## 7. Экран разрешений Windows/macOS

Для каждой способности вести отдельное состояние: `granted`, `denied`, `not_determined`, `unavailable`, `needs_live_test`, `unknown`. Не сводить неизвестное состояние к «разрешено».

Первичный список: запись экрана, камера, микрофон, местоположение, специальные возможности/управление интерфейсом, доступ к файлам. Матрицу уточнить по реально используемым API в каждом агенте.

Экран бота для каждой возможности:

- что она делает и работает ли на этой ОС;
- проверенное состояние и время последней проверки;
- кнопки **Повторить проверку**, **Открыть настройки** (deep link, где поддерживается), **Как разрешить**;
- для разрешения с ограниченной диагностикой — честная пометка «можно подтвердить только пробным действием».

Агент не может сам нажимать системное разрешение. После изменения настройки владелец возвращается в бота и запускает повторную проверку/пробное действие.

## 8. Системное местоположение и IP-fallback

Добавить платформенный адаптер для системной геолокации ОС с явным consent и таймаутом. macOS использует Core Location/поддерживаемый системный API, Windows — Windows Location API/поддерживаемый API. Точный пакет/bridge выбирается после технической проверки совместимости с текущими Python-агентами и упаковкой.

Результат всегда содержит источник и точность: `system_location` или `ip_estimate`. Если системная геолокация запрещена, отключена или недоступна, вернуть соответствующее состояние и по отдельному включаемому fallback — приблизительный IP-город/регион. Никогда не называть IP-оценку GPS, широтой/долготой GPS или точной координатой. В логе не сохранять координаты дольше необходимого; владельцу показывать последнее время получения и источник.

Приёмка: мок-тесты статусов/таймаутов, тест отказа в разрешении, интеграционный тест на ОС и физическая проверка на реальных Windows и Mac. Без физического теста статус — «код готов, ОС не принята».

## 9. Скриншот macOS

Разделить исходы: разрешение Screen Recording отозвано/не выдано, агент не в графической сессии, `screencapture` недоступен/завершился с ошибкой, пустой/нечитаемый файл, MQTT/загрузка результата неуспешны. Ответ бота должен показывать конкретную причину и вести к инструкции System Settings → Privacy & Security → Screen & System Audio Recording (точный путь сверить для версии macOS).

Проверить запуск агента через используемый LaunchAgent в активной пользовательской сессии, состояние после блокировки/сна/переключения пользователя, контроль размера и JPEG/PNG, очистку временного файла и таймаут. Не заявлять разрешение подтверждённым только по наличию процесса. Приёмка — локальный тест на Mac с фактическим снимком после выданного пользователем разрешения.

## 10. Одноразовое подтверждение произвольной команды

Перед выполнением shell-команды агент не получает её сразу. Владелец может создать запрос сам; пользователь с выданным shell-request grant может только отправить запрос владельцу. Бот формирует владельцу карточку с точным текстом команды, целевым устройством, отправителем, временем и кнопками **Выполнить** / **Отменить**. Подтвердить может только текущий владелец. Подтверждение:

- связано с неизменяемым хэшем команды, устройством и владельцем;
- одноразовое, с коротким TTL (предложение: 2 минуты), защищено случайным nonce и атомарно потребляется;
- теряет силу при смене устройства/команды, отзыве роли или перезапуске процесса;
- журналирует запрос, решение, исполнителя, устройство, время, exit code и ограниченный вывод с редактированием секретов;
- имеет таймаут, лимиты длины/stdout/stderr и сообщение о таймауте; команды `all` запрещены.

Для чужого запроса пользователь не может сам себя подтвердить; владельцу приходит карточка одобрения. Даже если запрос прислал сам владелец, карточка требует явного нажатия. Определённые кнопочные действия (перезапуск/обновление/питание) остаются allowlisted handlers и не превращаются в неограниченный shell.

**Уточнение доверия транспорта (добавлено после аудита реализации):** поскольку `SHARED_KEY` есть у сервера и обоих агентов, HMAC этого ключа не является доказательством серверного происхождения команды. Shell-команда получает отдельную подпись серверным приватным ключом, доступным только боту; агент проверяет подпись соответствующим публичным ключом, `request_id`, хэш точного текста, целевое устройство, TTL и одноразовое durable-потребление. Этот ключ не совпадает с ключом подписи GitHub Release и никогда не копируется на устройства. Если ключ/проверка отсутствуют или агент устарел, shell-команда отклоняется; остальные действия не меняют протокол.

## 11. Открытие сайта с агента

Доработать уже имеющийся поток «Открыть сайт», не создавать второй конкурирующий экран. Сохранить варианты количества `1/2/3/5`, если live-тест не выявит проблему; явно показать число, URL и устройство до запуска. Нормализатор URL и обработчики повторно проверить на всех состояниях формы и отозванных правах; разрешены только `https://` и `http://`, `file://`, `javascript:`, `data:` и неизвестные схемы запрещены. Повторное нажатие не должно незаметно дублировать операцию; добавить идемпотентность/дедупликацию там, где это совместимо с текущим MQTT protocol. Результат сообщает число реально запущенных окон, а не только факт публикации MQTT. Проверить default browser отдельно на Windows/macOS.

## 12. Сервер, журнал и диагностика

Серверный раздел отдельно показывает: состояние процесса бота, heartbeat MQTT/брокера, состояние VPS (если доступно), CPU/RAM/disk с временем замера, последние безопасные логи и релизные версии. Кнопки перезапуска, деплоя, обновления и отката доступны только владельцу с подтверждением; лог-вывод ограничен и очищен от токенов/паролей. Не показывать секреты `.env`, private keys или MQTT credentials.

Предлагаемые дополнительные функции:

1. «Последняя проверка» у каждой кнопки: когда, какая ОС/версия, результат и задержка.
2. Экспорт диагностического пакета без секретов: версии, platform capabilities, sanitized log tail, correlation IDs.
3. Canary-обновление: обновить одно выбранное устройство, дождаться heartbeat и smoke-check, затем разрешить массовое обновление; автоматический rollback при провале.
4. Дедупликация online/offline уведомлений по интервалу и heartbeat, чтобы один переход не слал десятки одинаковых сообщений.

## 14. Проверка качества и критерии готовности

### Автоматические проверки

- Unit-тесты рендеринга всех клавиатур под роли и grants; полный список callback-кнопок сопоставлен с категорией, OS support, разрешением и handler.
- Тесты доступа на UI и handler: owner/user/guest/blocked; отмена/expiry/повтор callback; отзыв права в процессе.
- Тесты одноразового terminal approval: неверный hash/device, истечение TTL, replay, отмена, concurrency, только owner; секреты не попадают в логи.
- Тесты permission-state mapping, location fallback/источника, ошибок скриншота, открытия URL/ограничения схем и числа окон.
- Регрессия всех существующих компонентных тестов; отдельно сравнить X-LEX данные, golden-тесты и поведение до/после — никаких изменений.
- Проверка RU/EN паритета и ссылок; build сайта; reduced-motion проверка.

### Приёмка по слоям

1. **Код:** тесты и статический анализ в CI прошли.
2. **Упаковка/релиз:** подписанный артефакт установленной версии проверяется по manifest/signature.
3. **Устройство:** реальный Mac и Windows выполняют ключевые функции с выданными разрешениями.
4. **Telegram:** владелец и тестовые роли проходят сквозные сценарии, одно сообщение не размножается, уведомления корректны.
5. **VPS:** health-check/логи/rollback проверены на реально доступном сервере.
6. **GitHub:** README/Pages/Release опубликованы и открываются.

Проект нельзя объявлять законченным, если какой-либо слой не проверен: его явно пометить как оставшийся блокер, не смешивая с успешными тестами кода.

## 15. Не входит в эту переделку

- Любое изменение X-LEX.
- Скрытие агента/companion-компонентов от владельца ОС, запрет локальной остановки/удаления, обход TCC/UAC или восстановление после удаления без явного согласия владельца.
- Автоматическая массовая раскатка без canary/health-check и подтверждаемого rollback.
- Утверждение, что живой VPS/Telegram/физический Mac/Windows проверены, если соответствующий smoke-тест не запускался.
