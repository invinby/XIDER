# TARPED — проект расширенной архитектуры и нового каталога возможностей

**Статус: спецификация одобрена владельцем 2026-10-15 для реализации. Публикация/деплой требуют отдельной проверки релизного gate и доступности целевой системы.**

## 1. Основа и цель

Этот документ расширяет исходную [спецификацию TARPED](2026-10-08-tarped-product-redesign-design.md), а не заменяет её. Все её требования сохраняются: навигация и экраны Telegram-бота, читаемые кнопки, неизменность X-LEX, RBAC, проверка разрешений, системная геолокация с явным IP-fallback, диагностика macOS screenshots, одноразовое подтверждение владельца для shell, RU/EN-паритет, доступная Pages-страница, диагностика, canary и честный health/rollback.

Точный novelty-базис — официальный `origin/main` commit `6d20370a06eb157428627f9002852514615e8ee2` (проверен 2026-10-15). Его родитель `f8e65a90031373372851a0d2096bec58ed070f92` содержит последний code-bearing change на main; сам базовый commit добавил только release notes. Последний успешно опубликованный GitHub Release на момент фиксации — v4.2.1; тег v4.2.2 уже существует, но пока не является опубликованным релизом. Расходящуюся Desktop-копию не сливать вслепую.

Цель расширения — превратить набор экранов в ясную структуру управления устройствами и добавить **30 отдельных, действительно новых функций в каждой из 17 продуктовых областей** (510 кандидатов всего). Переработка существующей кнопки, исправление неработающей функции, новое название или дополнительная настройка старого сценария в эти 30 не засчитываются.

## 2. Общее понимание и критерий «новое»

Ожидаемый результат: владелец видит короткие читаемые кнопки, быстро понимает результат и статус действия, а новые функции имеют отдельный пользовательский исход, тесты и проверяемую поддержку Windows/macOS. Разделы не должны превращаться в свалку из сотен кнопок: новые функции доступны через каталог раздела с поиском/страницами и карточкой конкретного действия.

Кандидат можно считать новым только если аудит `origin/main` не находит уже реализованного эквивалентного исхода в меню, callback/handler, worker command, Guardian command, серверном API, документации или релизном потоке. Для каждого принятого пункта Feature Registry хранит:

- постоянный `feature_id`, область, короткое название и понятное описание результата;
- доказательство отсутствия эквивалентной реализации в базовом commit;
- платформы и минимальные версии компонентов;
- роль/grant, требуемые разрешения и ограничения безопасности;
- компонент/интерфейс, который реализует функцию;
- unit/integration/acceptance-проверки и статус физического теста;
- идентификатор релизной партии, changelog и rollback-условие.

Если кандидат дублирует уже существующее поведение, его заменить до одобрения плана; не считать дубликаты за квоту. Улучшения и фиксы вести отдельным списком, не подменяя ими 510 новых возможностей.

## 4. Навигация и отображение Telegram

### 4.1 Контракт навигации

Построить navigation registry с идентификатором страницы, родителем, коротким label-id, callback, разрешёнными ролями/grants, целевыми платформами, требуемыми разрешениями и состоянием поддержки. Навигация выводит сначала цель/устройство, затем нужную область, затем действие; длинные версии, URL, объяснения и предупреждения остаются в тексте карточки, а не в подписи кнопки.

Главный экран группирует доступные владельцу и пользователю «Устройства», «Сервер», «Администрирование» и «Справка». Экран устройства содержит девять областей D01–D07, R01 и P01 как отдельные короткие входы; O01 доступна владельцу и ведёт в диагностику. B01/B02 — общий слой навигации и выбора устройства, а не дополнительные шумные кнопки в каждой карточке.

Обычный переход редактирует уже существующее сообщение бота, сохраняя один экран управления; отдельное сообщение допускается лишь для уведомления безопасности, ответа с файлом/фото или невозможности Telegram API отредактировать карточку. Для callback-ошибок есть идемпотентный fallback: обновить/пересоздать карточку и записать причину, не оставляя бесконечный progress loop.

### 4.2 Читаемость и совместимость X-LEX

Содержимое, словарь, существующие тексты, правила выбора стиля и runtime-поведение X-LEX заморожены. Сначала использовать уже имеющиеся короткие X-LEX labels; дополнительную информацию выносить в текст страницы. Новые labels для новых возможностей хранить в отдельном `Feature Catalog` resource с нейтральными короткими названиями, не редактируя X-LEX. Если новый сценарий требует X-LEX-копирайтинга, он остаётся вне данной реализации до отдельного согласования.

Проверка должна измерять подписи после локализации в Unicode grapheme clusters и UTF-16 units, не обрезать текст посередине слова/эмодзи, проверять ширины строк Telegram-клавиатур и скриншотные snapshot-тесты карточек. Короткая подпись не должна терять различие между командами; полное пояснение показывается перед опасным действием.

## 5. Инварианты безопасности и поведения

- X-LEX byte-for-byte и golden-output invariant: изменения контента/поведения запрещены.
- Все роли проверяются при построении UI, callback, продолжении FSM, перед публикацией команды и после отзыва права; `blocked` не получает действий.
- Системные разрешения никогда не обходятся и не выдаются агентом без пользователя; недоступность/неизвестность не маркируется как `granted`.
- Локация сообщает `system_location` с точностью/временем либо отдельно включённый грубый `ip_estimate`; IP не называется GPS.
- Скриншоты/камера/файлы имеют явный grant; ошибка сообщает причину и следующий шаг, секреты не попадают в логи.
- Произвольная терминальная команда всегда проходит одноразовое подтверждение текущего владельца на точный текст, устройство, hash и короткий TTL; подтверждение одноразовое, атомарное и аудируемое. Allowlisted кнопки остаются отдельными handlers.
- Guard Keeper — видимый компонент управления владельцем: без скрытого запуска, запрета локального удаления, скрытия от ОС и восстановления после удаления.
- Каждая обновляющая операция делает backup → install → функциональный health-check → commit активного слота либо rollback; canary precedes wider rollout.
- Публикация/деплой после каждой готовой партии допускаются только после её тестов, проверенного релизного артефакта и health-check; незавершённый тест или недоступный VPS не превращаются в фиктивный успех.

## 6. Архитектура компонентов

`X-STAB` (Telegram UI) отображает декларативный navigation registry и короткие callbacks. `X-CORE` проверяет RBAC/grants, формирует команды и связывает request/result. `X-MAP` остаётся источником платформенной поддержки/разрешений. `X-EDGE-W` и `X-EDGE-M` выполняют соответствующие операции. `X-GATE` реализует подтверждения владельца. `X-LEDGER` перечисляет совместимые версии, `TwinShift` выполняет staged update/rollback, `X-PROBE` проверяет функцию после запуска, `X-TRACE` хранит безопасный аудит, `X-VAULT` сохраняет проверяемую резервную копию. `X-LEX` остаётся неизменным.

Feature Catalog — декларативный реестр, а не динамическое исполнение кода из записи. Он описывает metadata и связывает каждую возможность с заранее зарегистрированным handler. Новый callback не может сам разрешать команду или обходить grants. Все изменения протокола версионируются и проверяют совместимость бота, агента и Guardian.

## 7. План проверок и критерии готовности

### Автоматические

- Baseline commit/hash, RBAC matrix и X-LEX hash/golden output сохранены до изменений.
- Для всех страниц/ролей строятся тестовые keyboard snapshots; каждый callback имеет ровно один зарегистрированный handler/доступ и каждый catalog item отображает support/evidence.
- 510 new-feature IDs уникальны; на каждую область ровно 30; novelty review содержит доказательство отсутствия в baseline; дубликаты приводят к замене кандидата.
- Инварианты разрешений, IP-fallback, системной геолокации, macOS capture errors, URL/power/shell, FSM revocation, повторных callbacks, one-message UI, canary/update/rollback тестируются отдельно.
- Проверки README/RU-EN, Mermaid, Pages build, reduced-motion, клавиатурных label-lengths и X-LEX regression выполняются в CI.
- Полный `python tools/run_tests.py`, `compileall`, Windows PowerShell parsing, Linux deployment fixtures и release-signature verification запускаются после реализации соответствующих партий.

### Приёмка

Отдельно фиксируются: (1) source/tests; (2) упаковка и подпись; (3) GitHub Pages/README; (4) GitHub Release; (5) live VPS health/update/rollback; (6) Telegram owner/user/guest/blocked и одна карточка; (7) физический Windows; (8) физический Mac. Тесты этого worktree на 2026-10-14: `python tools/run_tests.py` завершился с `PASS` на `685220a`; deployment/signature suite имел 27 условно пропущенных проверок, а Windows staged-install rollback fixture был пропущен без elevated PowerShell. Это не доказывает live/device приёмку.

### Публикация и deploy

Каждая завершённая и проверенная партия — самостоятельный release unit с коротким осмысленным changelog, тестовыми логами, digest/signature и rollback-ссылкой. Она публикуется в GitHub и затем разворачивается на VPS только из официального main/release artifact. После выкладки проверяются service health, текущий build и контрольный Telegram/MQTT health path; при ошибке выполняется rollback. Нельзя деплоить промежуточный код ради буквального «после каждого изменения» до того, как изменение стало проверяемой release-партией.

## 8. Исключения

Не меняются X-LEX и его golden tests; не добавляются скрытые/устойчивые к владельцу процессы; не обходятся ОС-подтверждения; не выполняются shell-команды без owner approval; не публикуются секреты; не объявляются физические/live проверки успешными по unit-тестам или наличию handler.

## 9. Этапы согласования

1. Владелец подтверждает или поправляет 17 областей и требование 30 новых функций в каждой.
2. Для каждого раздела готовится 30-пунктовый novelty-audited Feature Registry; каждый пункт получает ID, исход и тест.
3. Владелец проверяет полный письменный spec (эта архитектура плюс реестр) и утверждает его.
4. Только после этого составляется implementation plan по партиям/зависимостям, включая порядок GitHub/VPS публикаций; владелец отдельно утверждает план.
5. Только после одобрения плана разрешена реализация.

До прохождения шагов 1–4 этот документ остаётся черновиком, не является планом, коммитом, релизом или разрешением на deploy.

Первая сверка нашла шесть очевидных повторов: прежний D02-F10 с P01 permission-status; прежний W01-F03 с D01-F12; прежний W01-F30 с D01-F22; прежние M01-F13/M01-F14 с D06-F08/D01-F10; прежний O01-F28 с существующими correlation IDs. Владелец одобрил новые формулировки этих шести строк. Вторая сверка с кодом нашла ещё четыре: прежний B01-F12 повторял выбор устройства через `menu:target`; прежние D06-F11/F21 повторяли Guardian status payload (версия/процесс/регистрация системной задачи); прежний R01-F07 повторял уже показываемую signature state карточку релиза. Владелец одобрил четыре замены (предупреждение о незавершённом вводе, целостность Keeper, согласованность Guardian state journal и тренд размера подписанных release assets). Также D05-F28 заменён и одобрен на отчёт двух измеримых shell-интервалов; D03-F27 заменён и одобрен на владельческий staging inbox. Это не доказательство, что остальные пункты прошли полную семантическую проверку; аудит продолжается.

Ещё один точечный overlap: прежний D05-F28 предлагал единый correlation ID для пути request → approval → publish → result, но базовый код уже передаёт `request_id`/`command_id` через pending approval, transport и agent result; в `bot.py` есть tracked-response collectors и audit events. Значит сам ID нельзя считать новой функцией. `access_store.append_command_audit()` сохраняет UTC epoch `at` и статусы `attempting`, `sent` и конечный исход по `request_id`. Владелец одобрил замену на read-only отчёт только по двум доступным интервалам: `attempting → sent` (dispatch) и `sent → terminal result`. Время от создания запроса до approval не сохраняется, поэтому в метрику не входит и отчёт не должен его подразумевать.

Для B02 проверены `TG-BOT-SERVER/device_store.py` и основные клавиатуры `devices_menu()`, `admin_devices_menu()` и `guest_devices_menu()` в `bot.py`. Базовый `DeviceStore` хранит heartbeat/сведения устройства, поддерживает получение списка/карточки, переименование, удаление записи и избранные команды; в проверенных меню каталог выводится списком без поиска, фильтров, коллекций, пользовательского порядка, заметок или архивирования. В этом узком source audit прямых совпадений B02-кандидатов не найдено. Внутри кандидатов F07 определён как произвольный многозначный набор пользовательских ярлыков, а F20 — одно нормализованное поле назначения; коллекции F08 — вручную собранные списки, сохранённые фильтры F09 — повторяемый запрос, порядок F12 — ручная позиция, сортировка F10 — вычисляемый порядок. Это разводит близкие концепции, но не доказывает уникальность всех 30 пунктов.

Для D01 проверены существующие одноразовые команды `sysinfo`, `battery`, `disks`, `storage_smart`, `sys_installed_apps` и `sys_uptime` на обеих платформах. Они дают текущий снимок: например, battery payload содержит доступность, процент, подключение к питанию и оценку времени, но не историю здоровья/износа; `sys_uptime` показывает длительность работы, но не историю загрузок; disk и SMART-команды не сохраняют временные ряды. Поэтому история/сравнение/тренд в D01 — отдельный исход, пока каталог не обещает период до появления нескольких локальных снимков. Слова «если ОС поддерживает» и явное отсутствие датчиков должны сохраниться для температур, памяти и energy source; одноразовый аналог сам по себе не делает исторический отчёт дублем. Это audit границ, а не проверка всех 30 D01 пунктов на платформенных API.

Для D03 подтверждены текущие операции `dir_list`, `find_file`, `path_open`, `file_get`, `file_put` и `file_del` в обоих агентах и меню файлов бота. Ответ `dir_list` уже содержит имя, признак папки, размер для файла и ограничение выдачи; поэтому D03-F09 уточнён до дополнительных временных/доступных атрибутов, а не базовых имени/типа/размера. D03-F27 («сканирование опасных путей») является обязательным приёмочным свойством безопасной распаковки D03-F26, а не отдельной пользовательской функцией-кандидатом. Владелец одобрил замену на отложенный inbox для файлов, переданных им через Telegram: принять в отдельную staging-область устройства, показать очередь/метаданные, затем явно разместить в выбранном пути или удалить; не запускать и не открывать содержимое автоматически. Это отдельный исход от журнала файловых операций D03-F24.

Для D04 в обеих платформах подтверждены разовый снимок интерфейсов/счётчиков (`network`), Wi‑Fi SSID/сигнал (`wifi_info`), внешний IP (`ext_ip`), TCP-соединения (`netstat`) и единичный ping четырьмя пакетами к заданному handler-ом хосту. Это не хранит историю измерений, DNS/route/TLS-отчёты или оповещение о смене внешнего IP; их нельзя считать реализованными только из-за текущего snapshot или одного ping. При этом endpoint-ы для новых проверок должны оставаться явно заданными владельцем, с ограниченными timeout/объёмом, без перебора адресов/портов.

В D05 проверена текущая команда shell: запрос получает короткоживущий `request_id` и точный текст, owner получает одноразовые кнопки approve/cancel, а результат возвращается в ту же карточку с кодом/статусом и redaction. Поэтому прежний D05-F19 («отменить ожидающий запрос») уже реализован через owner-only `cmd:shell-cancel:<request_id>` и является прямым дублем. Владелец одобрил замену на сводный owner-only inbox ещё не истёкших pending approvals с устройством, инициатором, возрастом/сроком и открытием точного неизменённого preview; сам список не исполняет команду и не даёт approve без прежнего одноразового callback.

Для S01 проверены `server_ops.metrics()`, `server_metrics_text()` и отображение графика. Сейчас сохраняются до 60 снимков CPU-нормализованного load average, RAM и `/` disk; текст прямо предупреждает, что load не является CPU usage. Поэтому прежний S01-F17 с ещё одной интерпретацией load/core семантически дублирует текущую метрику. Владелец одобрил замену на тренд CPU Pressure Stall Information (PSI) из `/proc/pressure/cpu`; если источник недоступен на ядре/хостинге, интерфейс должен показывать `unsupported`, а не ноль.

Для A01 проверены `access_store.py` и административные handlers в `bot.py`. Роли owner/user/guest и специальное состояние blocked уже действуют; owner определяется конфигурацией, назначить/заблокировать его нельзя. Выдачи callback/device грантов и блокировка проходят отдельный одноразовый owner-confirm, затем повторно сверяется snapshot перед изменением. Причина блокировки сейчас не запрашивается; grants без срока; named profiles, dry-run bulk changes и access request queue в проверенных handlers не обнаружены. Пользовательский список выводит до 30 записей, а журнал — последние 12 строк без фильтров/экспорта и без карточки детализации; записи изменений ролей и grants уже ведутся. Поэтому F09, F13–F15 остаются потенциально новыми; они не должны дублировать существующий базовый журнал. F27 (owner invariant) не должен трактоваться как замена реальной защиты: проверенные mutators/filter-ы уже защищают owner, а отдельная owner-only проверка была бы диагностикой текущей конфигурации. Это source audit конкретных хранилища и handlers, не полный тест RBAC.

Для D02 уже подтверждены экранный/камерный/микрофонный одиночные capture и простое изменение системных параметров. Поэтому прежние F04 (формат изображения), F06 (курсор), F13 (размер/качество одного кадра), F21 (контейнер той же записи), F22 (лимит длительности того же запроса) и F26 (сохранённые уровни яркости) признаны параметрами/предустановками существующих действий и заменены по одобрению владельца: F04 — ручная маскировка выбранных областей на копии скриншота с preview до отправки; F06 — подписанный контактный лист с явно выбранных мониторов; F13 — однокадровая локальная проверка резкости/экспозиции без сохранения кадра; F21 — локальная проверка баланса аудиоканалов с удалением временного образца; F22 — owner-controlled отмена активного media-запроса с честным terminal status; F26 — экспорт/импорт пользовательского профиля дисплея с preview и подтверждением применения. Все шесть замен одобрены владельцем. F05 (явный preview до отправки) — отдельный workflow: текущий screenshot handler отправляет результат напрямую. Ни одна из новых строк пока не реализована.

Для P01 текущая capability-карточка, platform help/settings переход, ручная повторная проверка и отдельное нажатие IP fallback уже существуют. Поэтому простой повтор F09 и простой выбор источника в F25 не новы. Владелец одобрил замену F09 на одноразовую проверку, связанную с конкретным переходом в настройки и свежим ответом; отсутствие ответа остаётся unknown. F25 заменён на owner-requested side-by-side сравнение system-location и IP estimate с source/accuracy, без хранения координат. Это не фоновый tracking и не автоматический fallback. F07/F08 должны описывать соответственно точную диагностику по OS/build и preview конкретной панели, а не повторять текущую справку/переход. F20 также пересекается с текущим разделением capability declarations и permission snapshot и требует отдельного source review.

Источники находок в baseline: `XGENT-MCS/xgent_mcs.py` и `XGENT-WDS/xgent_wds.py` регистрируют команды D02/P01; `TG-BOT-SERVER/bot.py` содержит соответствующие callbacks/handlers, включая capability help/settings, repeat check, отдельный IP-fallback, `publish_tracked()` и shell approval/result flow; `TG-BOT-SERVER/check_store.py` хранит `correlation_id` и latency ограниченных read-only checks; `TG-BOT-SERVER/access_store.py::append_command_audit()` хранит `at` и статусы shell execution по `request_id`. Создание shell-запроса до owner approval в typed audit не записывается.

## Приложение R — результаты заключительного source audit

**D04-F21 baseline audit:** `git grep -in -E 'link.speed|link_speed|interface_speed' origin/main -- TG-BOT-SERVER XGENT-WDS XGENT-MCS` returned no link-speed feature at the approved baseline. The implementation reads only the selected adapter's OS-reported `psutil.net_if_stats().speed` (Mbps), requires an up interface, and returns `unsupported` rather than inventing zero when the OS does not expose a valid speed. This link-layer value is explicitly not internet throughput.

**D04-F22 ruling:** implement “route table view” as a one-shot lookup for one owner-supplied literal unicast IP. Ask the OS which route, gateway, and interface it would select; do not send packets to the destination. Reject hostnames, scoped IPv6 strings, unspecified and multicast addresses. The result is read-only and reports `unknown`/`unsupported` if the platform cannot provide a valid route. This is distinct from D04-F09 traceroute, which sends bounded network probes.
**D04-F22 baseline audit:** `git grep -in -E 'route.table|route_table|Get-NetRoute|Find-NetRoute|netstat -rn|routing table' origin/main -- TG-BOT-SERVER XGENT-WDS XGENT-MCS` found only the default-gateway probe; no destination-specific route lookup exists in the approved baseline.

**D05-F28 baseline audit:** existing shell audit rows persist integer-second `attempting`, `sent`, and terminal statuses keyed by request ID, but no summary computes execution intervals. The report groups only consistent command-execution audit rows and computes `attempting → sent` plus `sent → terminal result`; it excludes request-to-approval time because that interval is not recorded. Output is aggregate counts/mean/median/max with one-second resolution and never returns command text, hashes, request IDs, device IDs, or raw audit rows.
