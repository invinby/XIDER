# XIDER Mega Roadmap

Единый план проекта. Это рабочий документ: он отделяет уже сделанное от того,
что нужно проверить, исправить или спроектировать. Наличие пункта в этом файле
не означает, что функция уже работает.

## 0. Идея проекта

XIDER — личная система управления собственными компьютерами через Telegram.
В состав входят Telegram-бот, VPS-сервер, MQTT-транспорт, Windows-агент,
macOS-агент, Guard Keeper и система релизов.

Цель проекта — не набор случайных кнопок, а аккуратная экосистема, в которой:

- каждая функция имеет понятное назначение;
- каждая часть имеет собственное осмысленное имя;
- все действия выполняются через кнопки;
- опасные действия требуют ясного подтверждения;
- устройство, сервер и агент показывают правдивый статус;
- обновление можно проверить и откатить;
- настройки и секреты не теряются при повторной установке;
- тексты и визуальный стиль управляются централизованно;
- неизвестная или нестабильная функция честно помечается.

## 2. Архитектура

### Бот

- один основной Telegram-процесс;
- один диспетчер команд;
- единая навигационная карточка на чат;
- отдельные callback-группы для меню, устройств, сервера и админки;
- FSM только для ввода параметров;
- никаких секретов в сообщениях;
- все действия проходят X-GATE.

### VPS

- `xider-bot.service`;
- MQTT TLS-соединение;
- хранение ролей, устройств, настроек и журналов;
- backup перед изменениями;
- проверка здоровья после перезапуска;
- понятная серверная в Telegram.

### Агент

- один основной процесс агента;
- отдельный Guard Keeper;
- heartbeat;
- reconnect с backoff;
- ответ на команду с correlation id;
- карта поддерживаемых возможностей;
- локальный журнал без токенов;
- автозапуск через штатный механизм ОС.

## 3. Главное меню бота

Переделать `/start` и главное меню так, чтобы оно всегда:

- отвечало в чистом чате;
- создавало новую карточку, если старая удалена;
- удаляло или заменяло старую карточку без дублей;
- показывало роль владельца;
- показывало количество устройств online;
- показывало версию бота;
- не зависело от устаревшего `message_id`;
- имело рабочие кнопки во всех стилях.

Главные разделы:

1. Устройства.
2. Серверная.
3. Обновления.
4. Guardian.
5. Админка.
6. X-LEX.
7. Настройки текста и стиля.

## 5. Аудит функций агентов

Каждая кнопка должна иметь статус в X-MAP:

- `stable` — проверено на этой ОС;
- `partial` — работает с ограничениями;
- `experimental` — требует ручной проверки;
- `unsupported` — ОС не поддерживает;
- `offline` — агент не ответил;
- `permission` — нет разрешения ОС.

## 6. Геолокация

Не обещать точный GPS, если агент его не получает. X-MAP должен различать:

- GPS;
- разрешённую системную геопозицию;
- приблизительную IP-локацию;
- отсутствие данных.

Для каждого результата показывать источник, точность и время получения.

## 7. Роли и админка

### Роли

- **гость** — видит разрешённые разделы, ничего не меняет;
- **пользователь** — получает отдельные кнопки и устройства;
- **владелец** — полный доступ, кроме невозможности случайно заблокировать самого себя.

### Функции админки

- список выданных устройств;

- блокировка;
- разблокировка;
- выдача прав на кнопку;
- выдача прав на устройство;
- журнал действий;
- уведомление владельцу о новом `/start`;
- просмотр сообщений пользователя;
- отправка ответа пользователю;
- редактирование текстов;
- выбор стиля пользователя или всего бота.

## 9. Обновления и TwinShift

Поток обновления:

1. получить список релизов из GitHub;
2. проверить компонент и ОС;
3. проверить совместимость протокола;
4. показать описание версии;
5. создать backup;
6. скачать в неактивный слот;
7. проверить digest и содержимое;
8. сохранить `.env` и локальные настройки;
9. установить новый слот;
10. запустить;
11. выполнить X-PROBE;
12. переключить слот;
13. при ошибке автоматически вернуть предыдущий;
14. записать результат в X-TRACE;
15. показать один итоговый ответ в Telegram.

Нельзя считать обновление успешным только потому, что процесс запустился.

## 10. Guard Keeper

Guard Keeper должен:

- видеть состояние основного агента;
- отличать штатную остановку от падения;
- отправлять heartbeat;
- запускать восстановление после сбоя;
- не создавать дубли процессов;
- показывать последнюю причину восстановления;
- иметь status/start/stop/restart;
- иметь режим auto-recovery;
- обновляться отдельно от агента;
- иметь собственный health-check;
- не хранить токены в логах.

Для Windows — Task Scheduler. Для macOS — LaunchAgent. Нужна проверка после
перезагрузки, выхода из сна, потери сети и ручной остановки агента.

## 11. Установка и короткая команда

X-DOCK должен свести установку к одной короткой команде для Windows и macOS.

Требования:

- не использовать случайные текущие каталоги;
- создавать каталог до копирования `.env`;
- не удалять `.env` при повторной установке;
- не удалять рабочий агент до проверки нового;
- показывать понятный этап ошибки;
- автоматически получать совместимую версию;
- не печатать секреты;
- поддерживать повторный запуск;
- после установки показать status и log path;
- уметь восстановиться после оборванной установки.

## 15. Правила версий

Использовать `major.minor.patch`:

- major — новая архитектура или несовместимый протокол;
- minor — группа новых функций;
- patch — исправления и небольшие улучшения.

Каждый релиз получает название, список изменений, известные ограничения,
совместимость и способ отката. Никаких случайных чисел и скачков версий.

## 16. Правило готовности

Функция считается готовой только если:

- код существует;
- есть локальный тест;
- есть корректный ответ бота;
- есть ответ агента;
- проверен результат на целевой ОС;
- ошибка понятна пользователю;
- действие записывается в журнал;
- повторный запуск не создаёт дубль;
- обновление и откат не ломают конфигурацию.
