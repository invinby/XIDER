# TARPED 4.1.0: установка Mac и обновления из Telegram

## Однократная подготовка

Короткая точка входа после публикации GitHub Pages:

```sh
curl -fsSL https://invinby.github.io/XIDER/mac | bash
```

Установщик проверяет подпись установочного скрипта, затем подпись bootstrap,
связавшую его SHA-256 с тегом и полным Git commit. Исходники скачиваются из
этого commit, а локальный recovery-пакет отдельно проверяется по подписанному
release manifest. Владелец не переносит `.env` или SSH-ключ с другого компьютера:
существующая конфигурация сохраняется; при первой установке разрешённые настройки
агента читаются через SSH с VPS. `BOT_TOKEN` в агент не передаётся.

Текущий сервер установки: `ubuntu@16.16.200.207`. Настройки можно явно изменить
через `XIDER_SERVER_HOST` / `XIDER_SERVER_USER`. Получение конфигурации требует
SSH-ключа/ssh-agent или ввода пароля VPS. Требуются Python 3, curl, unzip и OpenSSH.
Системные разрешения macOS нельзя автоматически подтвердить: доступ к экрану,
камере и микрофону выдаёт пользователь на самом Mac.

До остановки прежней версии подготавливаются зависимости и проверяется синтаксис
нового кода. Python-окружение хранится по стабильному пути `~/XIDER/runtimes/`:
его абсолютные пути не ломаются при замене checkout. Старые исходники и runtime
остаются для восстановления. Если активация процесса не прошла, установщик
возвращает прежнюю папку и пытается запустить прежнюю версию.

Успех установки означает запуск процессов Agent/Guard Keeper, не доказательство
работы всех функций устройства. MQTT, системные разрешения и реальные команды
проверяются отдельно по карточке устройства и журналу.

## После установки

В боте: устройство → версии → агент → список релизов → описание → установка →
подтверждение. Можно выбрать опубликованную совместимую версию с подписанным
`XIDER-source.zip`; простого тега без файлов недостаточно.

Обновления сериализованы. Файлы проверяются, сохраняется резервная копия и журнал
транзакции. Перезапуск заменяет текущий процесс через `exec`, не создавая второй
процесс, который проигрывает singleton-блокировку ещё живому старому агенту.
Старая MQTT-сессия не может выдать себя за здоровую новую версию. Recovery-пакет
переключается только после проверки новой версии. Ошибка запуска/связи оставляет
путь для отката по журналу, а не ложный ответ «всё обновлено».

Если новая версия меняет `requirements.txt`, текущий source-updater отклоняет
установку до замены файлов. Для такой смены окружения пока нужен установщик;
транзакционная дистанционная замена runtime остаётся отдельной задачей.
PyInstaller-бинарники этим source-updater не обновляются.

## Guard Keeper и восстановление файлов

Guard Keeper восстанавливает отсутствующие файлы агента из локального
подписанного пакета в `~/.xgent/recovery/`, а не из произвольной копии checkout.
Перед восстановлением он повторно проверяет подпись, размер, SHA-256 и допустимые
пути; оставшиеся файлы должны соответствовать той же версии. Секреты, `.env`
и Python-окружение из пакета не восстанавливаются.

Для восстановления нужен работающий Guardian и его runtime. Если удалить самого
Guardian, Python-окружение или всё состояние установки, эта схема не сможет
сама себя запустить. Явная остановка и полное удаление должны сохранять действие.
Это обычный supervisor, а не защита от владельца или администратора ОС.

Если worker пропал посреди незавершённого обновления, Guardian использует ту же
singleton-блокировку, что и worker: пока её держит живой процесс, файлы не
меняются. При свободной блокировке проверяется журнал и возвращается предыдущая
согласованная версия, затем восстанавливаются её недостающие файлы. Повреждённый
журнал или явная остановка запрещают восстановление.

Поздние ошибки перезапуска и незавершённого удаления бот сообщает владельцу
отдельно; одинаковая повторная доставка MQTT не создаёт новые уведомления.
Промежуточное «удаление подготовлено» не считается окончательным удалением.

## Safari и Siri: цепочка наблюдения macOS

Это внутренние имена XIDER-компонентов, не продукты Apple. Задуманная владельцем
цепочка — **Siri → Safari → Guard Keeper → Agent**: Siri наблюдает Safari; Safari
наблюдает Guard Keeper; Guard Keeper уже контролирует рабочий агент. Каждый уровень
передаёт следующему статус, последнюю ошибку и результат восстановления, чтобы бот
мог показать, где именно оборвалась цепочка.

Контуры ответственности должны оставаться однонаправленными: нижний уровень не
перезапускает верхний, а соседние процессы не поднимают друг друга по кругу.
Siri восстанавливает только Safari, Safari — только Guard Keeper, Guard Keeper —
только Agent. Перед запуском любого нижнего уровня проверяется сохранённое намерение
владельца; явная остановка или удаление выключает восстановление и не отменяется
наблюдателем. Службы регистрируются с понятными XIDER-именами в `launchd`, имеют
отдельные версии и журналы, отображаются в разделе компонентов бота и удаляются
штатным uninstall-командом.

**Статус реализации:** исходники видимых служб Safari/Siri, LaunchAgent-скрипты,
передача их собственного статуса в карточку устройства, ограниченные журналы и
включение компонентов в macOS bundle добавлены в локальную ветку. CI-сборка,
подписание/notarization, публикация релиза, установка на физический Mac и проверка
восстановления ещё не подтверждены. Пока агент не прислал свежий собственный health
record, бот показывает неизвестное/устаревшее состояние; версия Agent не подставляется
за версию Safari или Siri.

Подписанный macOS ZIP теперь собирает Siri/Safari supervisor в `XIDER-Layers.app`
и не должен содержать его три исходных entrypoint-файла в корне пакета; установщик
удаляет локальный `xider_layers.py` и отключает source-fallback для релизной установки.
Это убирает plaintext supervisor из пакета, но **не завершает обфускацию всего
устанавливаемого проекта**: текущий bootstrap всё ещё получает исходный checkout,
а бинарники PyInstaller сами по себе не являются защитой от извлечения bytecode.
Релизную поставку всех компонентов без исходников и полноценный бинарный updater
нужно доделать отдельно.

## Непроверенное на реальном устройстве

Полный цикл выбранный релиз → новый процесс → MQTT-health → откат нужно выполнить
на доступном Mac. Офлайн-тесты, наличие release assets или `launchctl`-процесса
не заменяют эту приёмку. Камера, скриншоты, микрофон, геопозиция, питание и
демонстрационные экранные эффекты проверяются отдельными сценариями.
