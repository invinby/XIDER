# TARPED: установка Mac и обновления из Telegram

## Однократная подготовка

Короткая точка входа после публикации GitHub Pages:

```sh
curl -fsSL https://invinby.github.io/XIDER/mac | bash
```

Страница скачивает installer и detached-подпись, проверяет подпись закреплённым
ключом издателя, затем запускает installer. Installer проверяет подпись bootstrap,
SHA-256, тег и полный Git commit. Для signed release bootstrap проверяет
подписанный manifest и устанавливает Nuitka-приложения Agent, Guard Keeper и
Safari/Siri без Python-файлов в активной папке. Исходный checkout нужен bootstrap
только временно для проверки релизного пакета.

Bootstrap никогда не запрашивает SSH-пароль. При первой установке нужны один из
трёх источников конфигурации: готовый локальный `.env`, настроенный SSH-ключ/
ssh-agent либо `XIDER_DOCK_URL`. Pages-команда запускает подписанный installer;
релиз включает X-DOCK URL только если в GitHub Actions задан публичный variable
`XIDER_DOCK_URL`. Секреты в эту переменную не помещаются. Публичный endpoint и
Dynamic Security broker ещё не развёрнуты. Поэтому чистая установка без `.env` или SSH-ключа пока не готова;
если конфигурации нет, установщик останавливается до изменения активной версии.
`BOT_TOKEN` агенту не передаётся. Разрешения macOS на экран, камеру и микрофон
выдаёт пользователь на самом Mac.

Signed release проверяется до остановки прежней версии. Подпись manifest,
содержимое ZIP, codesign и notarization ticket проверяются до переключения папки.
Временный Python runtime нужен только для проверки и удаляется вместе со stage;
он не устанавливается рядом с релизом. Development-режим отдельно сохраняет
исходники и venv. При ошибке запуска установщик возвращает предыдущую папку.

Успех установки означает запуск процессов Agent/Guard Keeper, не доказательство
работы всех функций устройства. MQTT, системные разрешения и реальные команды
проверяются отдельно по карточке устройства и журналу.

## После установки

В боте: устройство → версии → агент → список релизов → описание → установка →
подтверждение. Frozen Mac Guardian принимает подписанный `XGENT-MCS-macos-bundle.zip`,
проверяет его manifest, Apple-подпись и ожидаемый digest, затем транзакционно
заменяет три `.app`. Новый Agent должен подтвердить свежий heartbeat; иначе Guardian
возвращает предыдущие приложения. Windows frozen-updater использует подписанный
Windows bundle и отдельную проверку состояния.

Обновления сериализованы. Frozen Mac-updater сохраняет предыдущий набор приложений,
проверяет новый процесс и возвращает старый bundle при провале health-проверки.
Source-updater отдельно использует журнал своей транзакции; эти два пути не следует
считать одним механизмом.

Обновление считается завершённым только после свежего health-ответа нового
процесса. Успешная загрузка ZIP или старт старого Guardian этого не доказывают.

## Guard Keeper и восстановление файлов

`guardian_recovery.py` умеет восстанавливать разрешённые source-файлы из локального
подписанного пакета в `~/.xgent/recovery/`, если такой пакет установлен. Текущий
bootstrap не подкладывает этот cache в signed Mac-релиз. В frozen-сборке запуск и
обновление идут через подписанные `.app` bundles. Если удалены Guardian или вся
папка приложений, удалённый self-repair не гарантируется — потребуется обычный
installer. Это видимые LaunchAgent-службы, а не защита от владельца или администратора ОС.

Явная остановка владельцем сохраняет выключенное состояние; надзорные службы не
должны отменять это решение. Удаление из системы выполняется штатным uninstall.

Если worker пропал посреди незавершённого обновления, Guardian использует ту же
singleton-блокировку, что и worker: пока её держит живой процесс, файлы не
меняются. При свободной блокировке проверяется журнал и возвращается предыдущая
согласованная версия, затем восстанавливаются её недостающие файлы. Повреждённый
журнал или явная остановка запрещают восстановление.

Поздние ошибки перезапуска и незавершённого удаления бот сообщает владельцу
отдельно; одинаковая повторная доставка MQTT не создаёт новые уведомления.
Промежуточное «удаление подготовлено» не считается окончательным удалением.

## Safari и Siri: цепочка наблюдения macOS

Это внутренние имена XIDER-компонентов, не продукты Apple. Задуманная владельцем
цепочка — **Siri → Safari → Guard Keeper → Agent**: Siri проверяет Safari; Safari
проверяет heartbeat Guard Keeper и Agent, но при проблеме Agent перезапускает только
Guard Keeper; Guard Keeper уже поднимает или восстанавливает Agent. Все четыре
компонента записывают в собственный health-файл свежесть и состояние остальных
трёх. Так каждый слой видит общую картину, а Guardian и бот могут показать, где
оборвалась связь.

Наблюдение взаимное, право ремонта направленное: нижний уровень не
перезапускает верхний, а соседние процессы не поднимают друг друга по кругу.
Siri восстанавливает только Safari, Safari — Guard Keeper, Guard Keeper — Agent.
Safari дополнительно замечает устаревший heartbeat Agent и передаёт восстановление
Guard Keeper. Перед запуском любого нижнего уровня проверяется сохранённое намерение
владельца; явная остановка или удаление выключает восстановление и не отменяется
наблюдателем. Службы регистрируются с понятными XIDER-именами в `launchd`, имеют
отдельные версии и журналы, отображаются в разделе компонентов бота и удаляются
штатным uninstall-командом.

`codex/tarped-resume-20261026` синхронизированы на `af5d1e2` на момент проверки.
Pages run `40455729236` прошёл. CI run `40455729522` ещё выполнялся: Unix installer
checks прошли, Python 3.11/3.12 component suites оставались активны. Отдельный
build run `40452870765` на ref `xider-local-prep-siri-safari-20261027` завершил
Nuitka-сборки Windows и macOS и упаковку компонентов; release gate был пропущен,
поскольку это не tag build. Его артефакты — тестовые, Mac-пакет unsigned; это не
подписанный распространяемый релиз. Apple signing/notarization, публичный
релиз, установка на физические устройства и восстановление на устройстве не
подтверждены. Пока устройство не прислало свежий собственный health record, бот
показывает неизвестное/устаревшее состояние; версия Agent не подставляется за
версию Safari или Siri.

В релизной поставке macOS Agent, Guard Keeper и Safari/Siri собраны в Nuitka
`.app`-бандлы; Windows Agent и Guard Keeper — в Nuitka `.exe`. Python-модули не
лежат отдельными `.py` рядом с запущенными приложениями. Safari и Siri входят в
`XIDER-Layers.app`, а Mac-updater заменяет подписанный набор приложений
транзакционно. Секреты остаются в `.env`/системном хранилище и не вшиваются в
бинарники.

Это компиляция, которая усложняет чтение, а не абсолютная защита от анализа.
Bootstrap и вспомогательные shell/PowerShell-установщики остаются читаемыми; их
подписи и хэши проверяют целостность, но не обфусцируют текст. Сетевая проверка
VPS `16.16.200.207` на 2026-10-27: TCP/22, 80 и 443 отвечают, TCP/8884
истёк по тайм-ауту. HTTPS-проверка IP завершилась
`SEC_E_WRONG_PRINCIPAL`; сертификат не подтверждает этот адрес. Поэтому открытые
80/443 не доказывают работу X-DOCK. В текущей среде нет SSH-ключа, а проверенный
пароль сервер отклонил. Для чистой одно-командной установки без SSH нужен
работающий X-DOCK endpoint, подтверждённый релиз и опубликованный
`XIDER_DOCK_URL`; этого сейчас нет.

## Непроверенное на реальном устройстве

Полный цикл выбранный релиз → новый процесс → MQTT-health → откат нужно выполнить
на доступном Mac. Офлайн-тесты, наличие release assets или `launchctl`-процесса
не заменяют эту приёмку. Камера, скриншоты, микрофон, геопозиция, питание и
демонстрационные экранные эффекты проверяются отдельными сценариями.
